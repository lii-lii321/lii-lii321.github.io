MathMaster Edu

一个数学错题本。拍照进来的一道错题，会在合适的时候重新出现在你面前—— 检索负责找到同类题，间隔重复负责决定什么时候出现。

01 — 问题

错题本都停在「收集」，没人真的复习

几乎所有错题本产品都把「记下来」当成终点：拍照、分类、存档、结束。 但真正决定提分的不是收集得多全，而是错题在什么时间点、以什么方式重新出现。 学生收藏了 300 道题，一道也没再看。

我自己就是这么废掉两本纸质错题本的。所以这个项目从第一天就定了一个约束： 系统必须主动决定「你什么时候该看哪道题」，而不是等学生来找。

「收集是最低成本的假努力。真正的产品价值在复习那一刻才发生。」
02 — 做法

三段式：检索、生成、调度

01

切分策略：把「一道题」当成原子单位

第一版按 512 token 切文档，题干和解法被劈成两半，检索出来的东西学生根本看不懂。 改成按题号 + 题干边界切分，再把解题过程作为附属块挂上去，召回率从 61% 直接到 88%。 这是整个项目里性价比最高的一次改动。

02

出题：不重复原题，但要同构

检索到同类题之后不是把原题再丢给学生，而是让模型按考查点重新生成一道， 避免学生靠记住答案过关。生成结果和原题一起入库，形成题簇。

03

调度：SM-2 + 一个「不熟练度」加权

纯 SM-2 对新用户不友好——前两周全是新题堆积。所以加了一层基于答题正确率和用时的 不熟练度权重，让队列在高难度和低难度之间保持平衡。

03 — 结果

19 个月后它长这样

88% 检索召回率 基线 61%
3.1k 注册学生 自然增长，无投放
23天 平均连续复习天数 行业中位数约 9 天

真正让我意外的不是用户量，是 23 天这个数字。 错题本类产品的续做率通常在第 4 天掉到谷底——因为学生发现「还是要做题」。 把难度压下来、反馈做得更即时之后，第 4 天的悬崖消失了。

踩过的坑（3 个，花了大概五周）
  • Streamlit 的状态管理：多步问卷式流程在 Streamlit 里极易出玄学 bug，最后把关键流程抽到独立的 FastAPI 服务上，前端只做渲染。
  • 向量库选型：一开始用 FAISS，本地跑得好好的，一换机器就丢索引。换成 ChromaDB 之后索引持久化成了配置里的一行字。
  • 题簇去重：同一道题被 OCR 识别出三种排版，题簇裂成三个，复习队列里连续出现三遍。加了题干归一化 + 相似度阈值合并才解决。

RAG 检索质量到底卡在哪一步

很多人做 RAG 做不好，第一反应是换模型、加 reranker、堆 prompt。 我把一次真实项目的召回失败逐层拆开后发现：八成的损失发生在最前面那一层。

2026-09-28· 阅读 12 分钟· # 精选· 最后更新 2026-10-01
目录
问题长什么样 第一层：数据被切错了 第二层：查询和文档不对称 第三层：向量本身不够好 第四层：根本没人在乎 我改了什么
358 用例覆盖
2,400 行后端
最后更新 10-01

问题长什么样

错题本上线两个月后，我开始收到一类反馈：学生说「搜出来的题跟我这道没关系」。 典型的 RAG 失败案例。但当我把 top-k 召回结果一条条捞出来人工看的时候， 发现了一个不太对的规律——

模型答得其实不差，检索才是重灾区。而且失败的分布非常集中： 凡是题干超过三行的、凡是带小问的、凡是答案和解析在文档里分得很开的，几乎全错。

先说结论

切分策略贡献了约 70% 的召回损失，reranker 只贡献了不到 10%。

我见过太多团队在这 10% 上花两周，在那 70% 上花两天。

第一层：数据被切错了

最初的实现很朴素：把所有上传的题目拼成一个大 Markdown，按 512 token、80 overlap 切。 听起来标准做法，实际上灾难。数学题的题干、已知条件、问法、解答过程分布在不同段落， 512 token 的窗口会从中间劈开一道题。 

chunker.tsbefore
// 切完之后向量里长这样：
[ "已知：△ABC 中，AB=AC，" ]   // ← 条件
[ "∠A=40°，求 ∠B 的度数。" ]      // ← 问法
[ "解：作 AD⊥BC 于 D …" ]        // ← 解法开头

// 检索"AB=AC" 命中的是第一块，
// 但学生真正想知道的是"∠A=40 求∠B"。

改法不复杂：先用正则把文档解析成结构化的「题目列表」，每一道题是一个完整单元， 连带它的解答、考点标签、难度等级。切分单位从 token 变成题目。 

chunker.tsafter
// 一道题 = 一个 chunk，不再被切开
{
  id: "q_8f21",
  stem: "已知 AB=AC，∠A=40°，求 ∠B 的度数。",
  solution: "作 AD⊥BC 于 D …",
  points: ["等腰三角形", "角度计算"],
  difficulty: 2,
  embedding: "…"   // 整题向量
}

第二层：查询和文档不对称

学生搜的是「我怎么做错了这道」，文档里存的是「这道题的完整解法」。 语义上不对称，embedding 天然对不上。解决办法是给每一道题额外生成一条 reframe 字段——把解题过程反向改写成「会导致哪些典型错误」， 和题干一起做双路召回。

检索的本质不是「找到相似的文本」，是「找到能回答这个问题的文本」。这两件事在数学题上差得很远。

第三层：向量本身不够好

换了切分策略之后，剩下的问题才开始显形：公式密集的题目，纯文本 embedding 明显弱。 我试过 bge-m3 加 reranker，收益大约 8%——值得做，但绝对不该是最先做的那件事。

踩坑提醒

一开始就上 reranker，等于在漏水的桶上贴金边。数据层的问题会被模型层的收益掩盖，然后一直掩盖到你上线。

我改了什么

阶段切分查询召回率
v1 基线512 token 固定窗口原始题干61%
v2 题目级切分按题号结构化原始题干88%
v3 双路召回按题号结构化题干 + reframe93%
v4 + reranker按题号结构化题干 + reframe96%

从 61% 到 96%，其中 27 个百分点来自改一个函数，2 个百分点来自换模型。 成本差了大概二十倍。

最后一条，跟技术无关

我们上线后做了三周的人工评测集，共 120 道题，两人独立标注。 我一直觉得这是「小题大做」，直到 v2 上线那天——评测集当场抓出了 9 个回归 bug， 其中 4 个是我肉眼完全看不出来的。

没有评测集的 RAG 调优，本质上是在许愿。

02 — 信息架构

五个一级入口，首页承担「10 秒内判断你是谁」的任务，关于页承担「给 HR 和合作方的尽调」任务。 博客和项目是两条独立的内容线，履历页从项目列表反向引用，不重复写。

03 — 设计令牌

颜色 / 字体 / 栅格

全部收进 src/styles/global.css 的 @theme，替换现有那套暗色变量。 强调色做成一等公民，一行 data-accent 属性就能切靛蓝 / 朱橙。

颜色 · 日间（默认）

令牌色值用途
--paper#FBFAF7页面底色。偏暖的米白，比纯白更适合长时间阅读，也更像纸
--paper-2#F3F1EA次级面：hover 态、代码块、CTA 底、迷你卡片
--paper-3#E9E6DC占位图底、头像底
--ink#15151A正文墨色、按钮底、分隔线强调（顶部 1px 实线）
--ink-2#4B4B55次要文字、摘要
--ink-3#8C8C96meta、日期、标签
--rule#E2DFD61px 发丝分隔线。整站不用阴影做层级，全靠线
--accent#2F4BFF / #D9481F强调色：链接、当前导航下划线、mark、引用块左侧。靛蓝或朱橙二选一
夜间模式

博客长文值得配一套夜间。令牌已在设计稿里验证：--paper:#0E0E11、--ink:#EDEAE3、 强调色自动提亮到 #8A9BFF。建议作为 v2 的第二阶段，不要第一版就做。

字体

层级字体规格用在哪
Display衬线 Noto Serif SC / Source Serif 4clamp(2.9rem, 7.4vw, 6.2rem) / 0.98 / -0.025em首页大标题、页面 H1
H1衬线 700clamp(2.1rem, 4.6vw, 3.6rem) / 1.08页面主标题
H2衬线 600clamp(1.5rem, 2.7vw, 2.1rem) / 1.18区块标题
Lede无衬线 4001.05–1.22rem / 1.72 / max 56ch首页与详情页导语
Body无衬线 4001.06rem / 1.9 / max 68ch文章正文、说明段
Meta等宽 JetBrains Mono11–12.5px / letter-spacing .04em / 大写日期、编号、标签、状态
Code等宽12.3px / 1.75代码块、行内 code

核心是衬线做标题、无衬线做正文、等宽做元信息的三层分工。 衬线给「刊物感」，等宽给「工程感」，这一层分工就是新版和旧版的根本差别—— 旧版只有无衬线，所以看着像工具站而不是个人站。

06 — 工程

内容模型与技术选型

继续沿用现有栈，不引入新框架。Astro 的静态输出 + Content Collections 天然就是为「个人博客 + 项目页」准备的。

内容存储理由
文章Astro Content Collections（src/content/blog/*.md）自带 frontmatter schema、Markdown 渲染、按日期排序
项目src/data/projects.json，与现有 travels.json 同构项目数量少、字段固定，JSON 比 Collection 更轻
个人信息src/config/site.ts 单一出口全站页脚、导航、meta 都读它，改名只改一处
简历public/resume.pdf不排版、不进版本库里改、HR 拿到的一定是对的
GitHub 数据构建时抓 → src/data/github.json静态页不需要运行时请求，零客户端 JS

SEO / 性能清单

每页唯一 title / description，模板 {page} · {name} · {tagline}Base.astro
OG 图 + Twitter card（博客详情页动态生成）Base.astro

RSS（@astrojs/rss）+ sitemap/rss.xml
