这个站的旅行板块有 11 本相册、340 张照片。它们的来源是一个 45.7GB、6746 张的原始图库——微信压缩图、单反原图、手机 HEIC 混在一起。让这堆照片「自己变成网站」，就是这篇要讲的管线。

## 设计约束：只读，不全量

第一条约束来自现实：**原始图库是唯一的真本，管线对它只能读、不能写**。全量上站不可行（45.7GB 没有任何静态托管理由地扛着它），手动挑选 340 张更不可行（永远排不上待办）。所以管线的形态是：

```text
原始图库（按行程分文件夹）
  └─ ingest：均匀抽样 → sharp 压缩（1600px / q80）→ 保留 EXIF → photos/<id>/
       └─ build-photos：读 EXIF → 缩略图 + 模糊占位 → travels.json → 页面与地图
```

`ingest` 只做一件事：把「行程文件夹」变成「相册」。上游的行程配置是一条数据：

```js
{
  id: 'yunnan',
  src: '云南 25.1.19-28',        // 原始图库里的文件夹名
  title: '云南环线：昆明 · 大理 · 丽江 · 西双版纳',
  date: '2025-01-19',
  place: { name: '大理古城', country: '中国', province: '云南', lng: 100.272, lat: 25.606 },
}
```

加一次旅行 = 加一条配置 + 跑一次脚本。成本压到这里，地图才活得下去。

## 抽样：均匀取样而不是随机

2833 张的云南怎么选出 32 张？随机取样会错过景点分布——照片在文件夹里天然按子文件夹（景点）聚簇，**均匀取样**天然尊重这个分布：

```js
function sampleEvenly(files, cap) {
  if (files.length <= cap) return files;
  const step = files.length / cap;
  return Array.from({ length: cap }, (_, i) => files[Math.floor(i * step)]);
}
```

按文件名排序后等距取点，丽江、大理、昆明的子文件夹都会被扫到。这不是最优解（封面级的「好照片」靠运气），但它无监督、可复现、零人工——对自动化管线，这三点比「选得好」重要。

## 压缩与 EXIF：一对矛盾

sharp 默认丢弃元数据，但站点下游还要读 EXIF 的拍摄时间。解法是一行：

```js
sharp(src)
  .resize({ width: 1600, fit: 'inside', withoutEnlargement: true })
  .jpeg({ quality: 80 })
  .withMetadata()   // 保留 EXIF，供下一级管线读取
  .toFile(out)
```

顺便验证了一个事实：<mark>微信传输会把 EXIF 的 GPS 字段剥掉</mark>——抽样检查 13 个文件夹的第一张照片，GPS 无一幸存。所以相册的地点坐标全部是人工标注在行程配置里的，EXIF 只贡献拍摄时间。自动化有边界，承认它比假装全自动更省事。

## 一条深坑：HEIC

青城后山那 24 张全部来自 iPhone，HEIC 格式（HEVC 压缩）。sharp 预编译包里的 libheif **没有内建 HEVC 解码器**（专利原因），报错是 `Support for this compression format has not been built in`。

<div class="callout">

**处置**：不在构建管线里硬啃解码依赖（为 24 张照片引入一串原生依赖不值得），该相册暂缺，用「手机端以兼容格式重导出」作为人工兜底。管线的鲁棒性不体现在什么都能处理，体现在坏一部分时其余照常工作——其余 11 本相册照常上站。

</div>

## 结果

| 环节 | 数字 |
|---|---|
| 原始图库 | 6746 张 / 45.7 GB（只读） |
| 入库 | 11 本相册 / 340 张 / 约 120 MB |
| 单册上限 | 32 张，均匀抽样 |
| 增量成本 | 一条行程配置 + 两次脚本 |

现在你在这个站的足迹地图上点开的每一张照片，背后都是这条管线在构建时算出来的——包括你正在读的这篇文章的封面逻辑。
